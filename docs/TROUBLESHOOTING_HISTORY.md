### #11 プロジェクト全体レビューに伴う品質向上とアーキテクチャ修正 (2026-05-11)
- **事象**: REVIEW_RESULT.md による多数の指摘（SettingsManagerのシングルトン崩壊、セキュリティリスク、型定義の二重管理、テスト欠落など）。
- **原因**: 急激な機能追加に伴う責務分離の不徹底および、 Electron/Node.js/React 間での型・インスタンス管理の乖離。
- **対処**:
    - **アーキテクチャ**: `electron/main.cjs` をリファクタリングし、`SettingsManager` のシングルトン化を徹底。IPCハンドラー間でのインスタンス共有を実現。
    - **セキュリティ**: `.gitignore` を更新し `credentials.json` を管理除外。CORS 制限を `localhost/127.0.0.1` に強化。
    - **品質**: 巨大コンポーネント `UnifiedEditor.tsx` をサブコンポーネントに分割。同期ファイル I/O を非同期化。 `any` 型の削減と共通ユーティリティ (`normalize.ts`) へのロジック集約。
    - **テスト**: `Vitest` を導入し、 `ScoringService` および `SettingsManager` のユニットテストを追加。重複していた E2E テストの整理とモックの修正。
    - **ドキュメント**: `README.md` と `SPECIFICATION.md` のバージョン不整合やタイポを修正。

## 2026-05-08: フィード未取得およびアプリ凍結障害

### 1. 起動時にフィードが表示されない (初期事象)
- **事象**: Windows起動後、アプリを立ち上げてもメイン画面にフィードが表示されず、背景のみの状態になる。
- **原因**: 
    1. 開発モード時の `data` ディレクトリのパス解決が不適切で、設定ファイルを読み込めていなかった。
    2. APIキーが `ScraperFacade` 内のサービスに正しく同期されていなかった。
    3. OS起動直後の不安定なネットワーク環境において、1回の取得失敗で処理が終了していた。
- **対処**: 
    - `electron/main.cjs` のパス計算ロジックを修正。
    - 起動時に API キーを強制同期する処理を追加。
    - `RSSFetcher.ts` に 3回のリトライロジックを実装。

### 2. データ鮮度フィルターによる全記事除外
- **事象**: パスや通信の問題を修正しても、依然として「No active signals detected」と表示される。
- **原因**: 
    - アプリの「90日以内の記事のみ表示」という仕様に対し、初期データの最終更新日が2024年であったため、2026年現在の実行環境ではすべての記事がフィルターされていた。
- **対処**: 
    - `ScraperFacade.ts` に、記事が0件の場合に期間制限を解除して再取得する「インテリジェント・フォールバック」を実装。

### 3. ファイル修正ミスによるメインプロセスのハング
- **事象**: 「接続不可」となり、Ctrl+Q による終了も効かない状態。
- **原因**: 
    - AIによるファイル編集時、`ScraperFacade.ts` の末尾に古いコードが重複して混入し、構文エラー（Syntax Error）が発生。
    - メインプロセスが初期化中にクラッシュ・停止したため、IPC通信やショートカット登録が機能しなくなった。
- **対処**: 
    - `ScraperFacade.ts` を物理的にクリーンアップし、重複コードを削除。
    - `npm run build:electron` によるビルド検証工程を厳格化。

### 4. 大量フィード取得時の通信ブロック
- **事象**: フィード116件の環境において、一部のサイトからアクセスが拒否される、または取得に極端に時間がかかる。
- **原因**: 
    - デフォルトの User-Agent (rss-parser) が一部のニュースサイトからボット判定され、403 Forbidden や 429 Rate Limit を受けていた。
    - サーバーの `0.0.0.0` バインドが一部の Windows セキュリティ設定と干渉。
- **対処**: 
    - `RSSFetcher.ts` の User-Agent を最新の Chrome (Windows) のものに変更。
    - 並列数を 20 に引き上げ、通信タイムアウトを 20秒に延長。
    - Fastify サーバーのバインド先を `127.0.0.1` に変更し、ローカル通信の確実性を向上。

### 5. 特定カテゴリの記事が「0件」と表示される
- **事象**: 「スマートリビング」「クリエイティブイメージング」「Eコマース」「先端マテリアル」の4カテゴリで、フィード設定があるにも関わらず記事が表示されない。
- **原因**: 
    1. ワークスペース内の `interests.json` が Mojibake しており、カテゴリ名が正しくマッチしていなかった。
    2. メインプロセスの `get-articles` IPC ハンドラーが「全カテゴリ合計で上位100件」のみを返していたため、記事数の多い「AI」や「ゲーム」カテゴリだけで枠が埋まり、マイナーなカテゴリが「沈黙」していた。
- **対処**: 
    - ワークスペースの設定ファイルをユーザー提供のクリーンなデータ（UTF-8）に同期。
    - `get-articles` の取得制限を 100件から **500件** に拡大し、全カテゴリの記事がフロントエンドに到達するように改善。
    - 診断スクリプト `verify_dashboard.cjs` を作成し、全カテゴリで記事が確保されていることを検証済み。

### 6. 再パッケージング後の「信号なし」表示（デグレード）
- **事象**: 最新版をインストールしても、依然として「No active signals detected」と表示される。
- **原因**: 
    - `electron/main.cjs` の `get-articles` IPC ハンドラーにおいて、表示制限を緩和する修正を行った際、肝心の記事取得を実行するコード（`const articles = await scraper...`）を誤って削除してしまっていた。
    - これにより `articles` 変数が未定義となり、ReferenceError が発生。内部の try-catch により `[]`（空配列）が返されていた。
- **対処**: 
    - `electron/main.cjs` を修正し、記事取得ロジックを正しく復旧。
    - 全ての IPC ハンドラーの記述を再点検。
    - 再度リリースビルドを行い、正常動作を確認。

### 7. UI表示設定が再起動後にリセットされる
- **事象**: 「JA Only」「表示サイズ」「Hide Image」の各設定が、アプリを再起動すると初期状態に戻ってしまう。
- **原因**: これらの設定がフロントエンド（React）のメモリ内ステートとしてのみ保持されており、ファイルシステムへの永続化ロジックが存在しなかった。
- **対処**: 
    - `data/ui_settings.json` を新設し、UI設定を保存する仕組みをバックエンド（SettingsManager）に実装。
    - `get-ui-settings` および `save-ui-settings` IPCハンドラーを追加。
    - フロントエンドの `App.tsx` において、起動時の設定復元と、変更時の自動保存（debounce処理付き）を実装。
    - TypeScript の型定義の不整合によるビルドエラーを修正し、安定したパッケージングを完了。

### 8. インストーラーのサイズ肥大化（145MB）
- **事象**: 配布用のインストーラー（.exe）のサイズが 145MB と大きく、ダウンロードや配布に時間がかかる。
- **原因**: 
    1. フロントエンド（Vite）およびバックエンド（esbuild）で既にバンドル済みのライブラリが、`node_modules` として重複してパッケージに含まれていた。
    2. `public` ディレクトリの内容が `dist` と重複してバンドルされていた。
    3. 圧縮設定が最適化されていなかった。
- **対処**: 
    - `package.json` の `dependencies` をすべて `devDependencies` に移動。配布パッケージから不要な `node_modules` を完全に排除。
    - `build.files` 設定を見直し、`public` の重複混入を防止。
    - `compression: maximum` を設定し、アーカイブの圧縮率を向上。
- **結果**: 
    - インストーラーサイズを **145MB → 114MB（約21%削減）** に改善。

### 9. インストーラー最適化に伴うアセット消失
- **事象**: パッケージング後にアプリアイコン、トレーアイコン、および一部のファビコンが表示されない、またはデフォルトに戻ってしまう。
- **原因**: 
    - `package.json` の `build.files` 設定において、重複排除のために `!public/**/*` を指定したが、Electron メインプロセス（`main.cjs`）が依然として `../public/` 配下のファイルを直接参照していたため、パッケージ内にファイルが存在せず読み込みに失敗していた。
- **対処**: 
    - `package.json` の `build.files` 設定を元に戻し、`public` ディレクトリを再度パッケージに含めるように修正。
    - `dependencies` の設定も安定性を考慮し、昨日の作業前の状態に復元。
    - インストーラーの `compression` 設定をデフォルトに戻し、ビルドの安定性を確保。

## 2026-05-09: Windows起動時のフィード表示遅延問題

### 10. Windows起動直後にフィードが表示されない
- **事象**: Windows起動時にアプリが自動起動（`--hidden`）する設定になっているが、その後トレイからアプリを開いてもフィードが表示されず、手動で更新されるまで最新情報が表示されない。
- **原因**: 
    1. Electron のメインプロセス（`main.cjs`）において、`app.setLoginItemSettings` による自動起動設定は行われていたが、バックグラウンド（非表示状態）でフィード取得を開始するトリガーが存在しなかった。
    2. フロントエンドが表示されるまで（IPCが呼び出されるまで）フィード取得が行われない設計になっていた。
    3. `--hidden` 引数で起動された際、一部の環境で `ready-to-show` イベントによって意図せずウィンドウが表示されてしまう可能性があった。
- **対処**: 
    - `main.cjs` の `app.whenReady()` 内で、バックグラウンドでのフィード取得（`scraper.fetchAndProcessArticlesWithFallback`）を即座に開始するロジックを追加。
    - `--hidden` 引数が指定されている場合、`ready-to-show` による自動表示を抑制し、トレイアイコンからの操作を待つように挙動を厳格化。
    - ウィンドウ表示制御ロジックを `createWindow` から `app.whenReady` 側のフローに統合し、初期表示の確実性を向上。

## 2026-05-09: 設定保存時の TypeError (sync-settings)

### 11. 設定保存時に "Cannot convert undefined or null to object" エラーが発生
- **事象**: Nexus Editor で設定を保存しようとすると、「Save Failed: Failed to save configuration: Error invoking remote method 'sync-settings': TypeError: Cannot convert undefined or null to object」というエラーが表示され、保存に失敗する。
- **原因**: 
    1. プロパティ名の不一致: フロントエンド（`nexusApi.ts`）は `feedConfig` というキーでデータを送信していたが、バックエンド（`SettingsManager.ts`）は `feed_urls` というキーでデストラクチャリングを行っていた。
    2. 防御的プログラミングの不足: `syncSettings` メソッド内で `Object.entries` や `Object.values` を呼び出す際、対象の変数が `undefined` または `null` である可能性を考慮したガード処理が不足していた。
- **対処**: 
    - `src/services/SettingsManager.ts` の `syncSettings` を修正し、`feedConfig` と `feed_urls` の両方のキーを許容するように変更。
    - `Object` メソッドを呼び出す前に、対象がオブジェクトであり `null` でないことを確認するガード条件（`actualFeeds || {}` 等）を追加。
    - 取得したフィード設定の各カテゴリデータに対しても、反復処理前に `if (!data) continue;` などのチェックを追加し、堅牢性を向上。

## 2026-05-09: フィード表示のデグレード問題

### 12. フィードに記事が表示されない ("No active signals detected")
- **事象**: バージョン 5.3.0 への更新後、メイン画面に記事が全く表示されず「No active signals detected」と表示されるデグレードが発生。
- **原因**: 
    1. カテゴリ判定の厳格一致: `ScraperFacade.ts` の `getDashboard` において、カテゴリ名が完全一致（`===`）する場合のみ記事を抽出していた。
    2. データ不整合によるマッチング失敗: 過去の `syncSettings` のバグや文字コードの微細な差異（Mojibake等）により、`interests.json` と `feed_config.json` のキー名に不一致が生じていた。
    3. 起動ロジックのミス: `main.cjs` の修正において、`--hidden` 引数がある場合にコンテンツのロード（`loadURL`）がスキップされるロジックミスが混入し、UIが正常に初期化されないケースがあった。
- **対処**: 
    - `ScraperFacade.ts` の `getDashboard` に **正規化マッチング（Normalized Name Matching）** を導入。記号、空白、全角/半角の差異を無視してカテゴリを照合するように改善。
    - `main.cjs` を修正し、ウィンドウの表示・非表示に関わらず常にコンテンツをロードするように初期化フローを修復。
    - `main.cjs` 内の重複した変数宣言（`isDev`）をクリーンアップし、ビルドエラーを解消。

## 2026-05-10: 更新ボタン押下時の初期化ダイアログ重複表示問題

### 13. 更新ボタン押下時に「既存の設定を検出」ダイアログが毎回表示される
- **事象**: 「更新」ボタンを押すたびに、初回起動時のみ表示されるべき「既存の設定を検出」ダイアログが表示されてしまう。また、ダイアログ内のボタン名が「Cancel / Confirm」であるのに対し、説明文では「『いいえ』を選択すると」となっており不整合があった。
- **原因**: 
    1. **フラグの非永続性**: 初期化済みフラグ（`nexus_initialized`）をブラウザの `localStorage` で管理していたが、一部の環境やリロード時にリセット、あるいは `useEffect` の競合により正しく参照・保持されないケースがあった。
    2. **ライフサイクル管理の不備**: `App.tsx` の `useEffect` 内で、非同期のダイアログ表示中に再度 `refetch`（loadingの変化）が発生すると、フラグが書き込まれる前に次のチェックが走り、ダイアログが重複してトリガーされる構造になっていた。
    3. **文言の不整合**: 日本語環境でのボタン名と説明文の不一致。
- **対処**: 
    - **ファイルベースの永続化に移行**: 初期化フラグを `localStorage` から、ファイルシステムに保存される `ui_settings.json`（`UiSettingsSchema`）に統合。これによりアプリの再起動やリロード、Electronのキャッシュクリアに左右されない確実な管理を実現。
    - **状態遷移の厳格化**: `App.tsx` の React ステートに `isInitialized` を追加。ロードされるまで（`null` の間）は初期化チェックをスキップし、一度 `true` になればそのセッションおよび次回以降もダイアログが絶対に出ないように修正。ダイアログで「キャンセル」を選択した場合でも、チェック完了とみなしてフラグを `true` に設定するようにロジックを補足。
    - **イベントハンドラのバグ修正**: `App.tsx` で `CustomDialog` に渡していた `onCancel` が `hideDialog` で固定されており、`useDialog` 内部の Promise resolve を実行する関数が呼び出されていなかった問題を修正。これによりキャンセル時も正しく状態が更新されるようになった。
    - **文言の修正**: ダイアログ内の説明を「『キャンセル』を選択すると」に修正し、実際のボタン名（Cancel）と一致させた。
    - **E2Eテストの更新**: `localStorage` を前提としていた既存のテストコードを、`nexusApi` のモックを使用する形式に刷新。

## 2026-05-10: AI Insights セクションの機能不足および情報の希薄化

### 14. AI Insights が常に空、または情報の具体性が低い
- **事象**: 「AI Insights」タブを開いても「No new trends discovered yet」と表示されたまま変化がない、あるいは抽出される情報の詳細度が低く、ユーザーにとっての実用性が不十分であった。
- **原因**: 
    1. **トリガーの不足**: トレンド抽出が `EvolutionJob` という定期実行ジョブ内でのみ行われており、ユーザーが任意のタイミングで探索を実行する手段が UI 上に存在しなかった。
    2. **データ構造の制約**: 抽出されたトレンドが「カテゴリ、理由、検知日」のみの単純な構造であり、なぜそれが重要なのか、どの程度の確信度があるのかといったインテリジェンスとしての付加価値が不足していた。
    3. **AIプロンプトの汎用性**: トレンド抽出用のプロンプトがシンプルすぎたため、Gemini 3.1 Pro/Flash の能力を十分に引き出せず、現在の興味設定に基づいた深い洞察が得られにくかった。
- **対処**: 
    - **データ構造の拡張**: `learned_keywords` に、トレンドの「タイプ（新興、躍進、専門、主流）」、「確信度（0-100%）」、「コンテキスト（抽出の根拠となった情報の断片）」を保持できるようスキーマを拡張。
    - **手動探索機能の実装**: UI に「Discover Trends Now」ボタンを追加。バックエンドに `/api/v5/discover-trends` エンドポイントを新設し、即時分析を可能にした。
    - **AIエンジンのアップグレード**: `GeminiService.ts` の `analyzeTrends` プロンプトを大幅に強化。「新奇性の発見」「パーソナライズ」「詳細な根拠」を重視する指示を与え、Gemini 3.1 Pro を優先的に使用するように変更。
    - **UI/UX の刷新**: カードデザインを「プロフェッショナルな AI 分析ツール」の質感へと刷新。確信度ゲージ、タイプ別バッジ、コンテキスト引用セクションを追加し、視覚的な情報密度と信頼性を向上。
    - **型安全性の確保**: `TrendSuggestion` インターフェースを定義し、関連コードから `any` を排除。厳格な型定義と lint 基準を遵守。
    - **検証の徹底**: `tests/e2e/ai_insights.test.ts` を新規作成し、トレンド探索からキーワード昇格、設定保存までの一連のフローが正常に動作することを Playwright による自動テストで実証済み。

### #15 プロジェクト全体レビューに伴う品質向上と大規模リファクタリング (2026-05-20)
- **事象**: REVIEW_RESULT.md による詳細な指摘事項（SettingsManagerのシングルトン崩壊、コンポーネント肥大化、テスト不足等）への包括的対応。
- **原因**: 開発スピード優先によるテクニカルデットの蓄積および、役割境界の曖昧化。
- **対処**:
    - **SettingsManagerのシングルトン化**: `ElectronSettingsManager` をシングルトンとして再設計し、ElectronメインプロセスとFastifyサーバー間で単一のインスタンスを共有するように修正。データの整合性と競合状態の解消を実現。
    - **コンポーネント分割**: 巨大な `UnifiedEditor.tsx` を機能単位（`SystemSettings`, `CategoryEditor`, `AIInsightsPanel`）に分割。`src/components/editors/` 配下へ整理し、可読性と保守性を大幅に向上。

    - **コードクリーンアップ**: 以前の独立サーバー構成の残骸や未使用のユーティリティ関数を削除し、プロジェクト構造をスリム化。
    - **ドキュメントの同期**: `docs/CODEMAPS/*` および `README.md` を最新の実装構造に合わせて全面的に刷新。シングルトン構成やコンポーネントツリーを正確に反映。
    - **品質検証**: ユニットテストに加え、`playwright` によるE2Eテスト、および規約に基づくリリースビルド (`npm run dist`) を実施し、デグレードがないことを確認済み。
