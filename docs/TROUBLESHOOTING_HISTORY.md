# Aegis Nexus 障害・トラブル対応記録

本ドキュメントは、発生した障害、その原因、および実施した対処を時系列で記録するものです。

---

## 2026-05-08: フィード未取得およびアプリ凍結障害

### 1. 起動時にフィードが表示されない (初期事象)
- **事象**: Windows起動後、アプリを立ち上げてもメイン画面にフィードが表示されず、背景のみの状態になる。
- **原因**: 
    1. 開発モード時の `data` ディレクトリのパス解決が不適切で、設定ファイルを読み込めていなかった。
    2. APIキーが `ScraperFacade` 内のサービスに正しく同期されていなかった。
    3. OS起動直後の不安定なネットワーク環境において、1回の取得失敗で処理が終了していた。
- **対処**: 
    - `electron/main.cjs` のパス計算ロジックを修正。
    - 起動時に API キーを強制同期する処理を追加。
    - `RSSFetcher.ts` に 3回のリトライロジックを実装。

### 2. データ鮮度フィルターによる全記事除外
- **事象**: パスや通信の問題を修正しても、依然として「No active signals detected」と表示される。
- **原因**: 
    - アプリの「90日以内の記事のみ表示」という仕様に対し、初期データの最終更新日が2024年であったため、2026年現在の実行環境ではすべての記事がフィルターされていた。
- **対処**: 
    - `ScraperFacade.ts` に、記事が0件の場合に期間制限を解除して再取得する「インテリジェント・フォールバック」を実装。

### 3. ファイル修正ミスによるメインプロセスのハング
- **事象**: 「接続不可」となり、Ctrl+Q による終了も効かない状態。
- **原因**: 
    - AIによるファイル編集時、`ScraperFacade.ts` の末尾に古いコードが重複して混入し、構文エラー（Syntax Error）が発生。
    - メインプロセスが初期化中にクラッシュ・停止したため、IPC通信やショートカット登録が機能しなくなった。
- **対処**: 
    - `ScraperFacade.ts` を物理的にクリーンアップし、重複コードを削除。
    - `npm run build:electron` によるビルド検証工程を厳格化。

### 4. 大量フィード取得時の通信ブロック
- **事象**: フィード116件の環境において、一部のサイトからアクセスが拒否される、または取得に極端に時間がかかる。
- **原因**: 
    - デフォルトの User-Agent (rss-parser) が一部のニュースサイトからボット判定され、403 Forbidden や 429 Rate Limit を受けていた。
    - サーバーの `0.0.0.0` バインドが一部の Windows セキュリティ設定と干渉。
- **対処**: 
    - `RSSFetcher.ts` の User-Agent を最新の Chrome (Windows) のものに変更。
    - 並列数を 20 に引き上げ、通信タイムアウトを 20秒に延長。
    - Fastify サーバーのバインド先を `127.0.0.1` に変更し、ローカル通信の確実性を向上。

### 5. 特定カテゴリの記事が「0件」と表示される
- **事象**: 「スマートリビング」「クリエイティブイメージング」「Eコマース」「先端マテリアル」の4カテゴリで、フィード設定があるにも関わらず記事が表示されない。
- **原因**: 
    1. ワークスペース内の `interests.json` が Mojibake しており、カテゴリ名が正しくマッチしていなかった。
    2. メインプロセスの `get-articles` IPC ハンドラーが「全カテゴリ合計で上位100件」のみを返していたため、記事数の多い「AI」や「ゲーム」カテゴリだけで枠が埋まり、マイナーなカテゴリが「沈黙」していた。
- **対処**: 
    - ワークスペースの設定ファイルをユーザー提供のクリーンなデータ（UTF-8）に同期。
    - `get-articles` の取得制限を 100件から **500件** に拡大し、全カテゴリの記事がフロントエンドに到達するように改善。
    - 診断スクリプト `verify_dashboard.cjs` を作成し、全カテゴリで記事が確保されていることを検証済み。

### 6. 再パッケージング後の「信号なし」表示（デグレード）
- **事象**: 最新版をインストールしても、依然として「No active signals detected」と表示される。
- **原因**: 
    - `electron/main.cjs` の `get-articles` IPC ハンドラーにおいて、表示制限を緩和する修正を行った際、肝心の記事取得を実行するコード（`const articles = await scraper...`）を誤って削除してしまっていた。
    - これにより `articles` 変数が未定義となり、ReferenceError が発生。内部の try-catch により `[]`（空配列）が返されていた。
- **対処**: 
    - `electron/main.cjs` を修正し、記事取得ロジックを正しく復旧。
    - 全ての IPC ハンドラーの記述を再点検。
    - 再度リリースビルドを行い、正常動作を確認。

### 7. UI表示設定が再起動後にリセットされる
- **事象**: 「JA Only」「表示サイズ」「Hide Image」の各設定が、アプリを再起動すると初期状態に戻ってしまう。
- **原因**: これらの設定がフロントエンド（React）のメモリ内ステートとしてのみ保持されており、ファイルシステムへの永続化ロジックが存在しなかった。
- **対処**: 
    - `data/ui_settings.json` を新設し、UI設定を保存する仕組みをバックエンド（SettingsManager）に実装。
    - `get-ui-settings` および `save-ui-settings` IPCハンドラーを追加。
    - フロントエンドの `App.tsx` において、起動時の設定復元と、変更時の自動保存（debounce処理付き）を実装。
    - TypeScript の型定義の不整合によるビルドエラーを修正し、安定したパッケージングを完了。

### 8. インストーラーのサイズ肥大化（145MB）
- **事象**: 配布用のインストーラー（.exe）のサイズが 145MB と大きく、ダウンロードや配布に時間がかかる。
- **原因**: 
    1. フロントエンド（Vite）およびバックエンド（esbuild）で既にバンドル済みのライブラリが、`node_modules` として重複してパッケージに含まれていた。
    2. `public` ディレクトリの内容が `dist` と重複してバンドルされていた。
    3. 圧縮設定が最適化されていなかった。
- **対処**: 
    - `package.json` の `dependencies` をすべて `devDependencies` に移動。配布パッケージから不要な `node_modules` を完全に排除。
    - `build.files` 設定を見直し、`public` の重複混入を防止。
    - `compression: maximum` を設定し、アーカイブの圧縮率を向上。
- **結果**: 
    - インストーラーサイズを **145MB → 114MB（約21%削減）** に改善。

### 9. インストーラー最適化に伴うアセット消失
- **事象**: パッケージング後にアプリアイコン、トレーアイコン、および一部のファビコンが表示されない、またはデフォルトに戻ってしまう。
- **原因**: 
    - `package.json` の `build.files` 設定において、重複排除のために `!public/**/*` を指定したが、Electron メインプロセス（`main.cjs`）が依然として `../public/` 配下のファイルを直接参照していたため、パッケージ内にファイルが存在せず読み込みに失敗していた。
- **対処**: 
    - `package.json` の `build.files` 設定を元に戻し、`public` ディレクトリを再度パッケージに含めるように修正。
    - `dependencies` の設定も安定性を考慮し、昨日の作業前の状態に復元。
    - インストーラーの `compression` 設定をデフォルトに戻し、ビルドの安定性を確保。
