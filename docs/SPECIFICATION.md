# Aegis Nexus 詳細外部仕様書 (v5.4.0)

本ドキュメントは、Aegis Nexusの全仕様を定義したものです。他言語への移行や再実装の際のマスター設計図として使用します。

---

## 1. システム概要
Aegis Nexusは、RSSフィードとGoogle Gemini 3.1 Proを統合し、ユーザーの関心に最適化されたニュースを収集・解析・提示する次世代インテリジェンス・コマンドセンターです。

### 1.1 コア・コンセプト
- **Signal vs Noise**: 大量の情報（Noise）から、AIを用いて価値ある情報（Signal）のみを抽出する。
- **Glassmorphism & OS Integration**: 透明感と深度を感じさせるUIと、Windows 11環境への高度な親和性。
- **Autonomous Agents**: 専門性を持った複数のAIエージェントが協調して動作する。
- **Comprehensiveness (網羅性の保証)**: AI探索において「提案0件」を排除し、常に有効な情報源を提供し続ける。

## 2. コア・ロジック仕様

### 2.1 記事収集・解析ワークフロー
1. **フィード取得**: `FeedManager` が管理するアクティブなURLからRSSを取得。
2. **カテゴリ判定 (`ScoringService`)**: 記事のタイトルと内容を、ユーザーが設定した各カテゴリの `brands` と `keywords` と照合し、最も一致するカテゴリを特定。
3. **スコアリング (`ScoringService`)**:
   - ベーススコア: 5点
   - ブランド一致: +10点
   - キーワード一致: +8点
   - 日付によるフィルタ: 90日以上前の記事は除外。
4. **エンリッチメント (`EnrichmentService`)**: 記事内から代表画像を抽出し、見栄えを向上させる。
5. **キュレーション (`GeminiService`)**: 上位30件の記事から、AIがさらに厳選した10件を選出し、推奨理由（Reasoning）を生成。

### 2.2 AI Suggest サービス (`GeminiService`)
- **Structured Output**: AIの自由な出力を禁じ、厳格なJSONスキーマ（ResponseSchema）に従わせる。
- **カテゴリ名整合性強制ロジック (Normalization)**: AIが再構築時に生成するカテゴリ名の微妙な表記揺れ（例：AIが「ロードバイク・MTB」を提案したが、既存設定は「ロードバイク・MTB・サイクリング」である等）を吸収するため、記号（＆, &, ・）や空白、大文字小文字を無視して比較・マッピングする `normalizeCategoryName` ロジックを導入。これにより、AIの出力の不確実性に関わらず、既存の購読フィードが正しいカテゴリへ確実に紐付けられ、記事が表示されなくなる問題を根本から解決。
- **データ完全保持リカバリーロジック**: `getRestructureProposal` において、AIが既存のブランドやキーワードをリストから漏らした場合でも、実行前の全データをバッファし、不足分を自動的に復元する。AIの推論による「情報の整理」と、システムによる「データの完全性保持」を両立。
- **柔軟な提案生成 (Schema Resilience)**: `brands` および `keywords` の提案スキーマにおいて、最小個数制約を `minItems: 5` から `minItems: 1` へと緩和。これにより、AIが特定のニッチなカテゴリで十分な候補を「絞り出せない」場合でも、パニック（空の出力やフォーマットエラー）を起こさず、見つかった分だけで正常に応答を返す堅牢性を確保。プロンプト上では引き続き「5つ」を目標として指示することで、質を維持しつつ安定性を向上させている。
- **動的APIキー同期と即時反映**: `SettingsManager` からのAPIキー変更を検知すると、再起動なしでシステム全体の `GeminiService` インスタンスに新しいキーが即座に反映される。特に、各IPCハンドラー（suggest-category等）の実行直前に `getApiKey()` を介して最新のキーをセットする実装により、ユーザーが設定を変更した直後のリクエストが古いキー（または空のキー）で失敗する問題を物理的に排除し、UXを劇的に改善している。

### 2.3 AI Insights (自律学習トレンド管理システム)
- **仕組み**: `ArchivistAgent` が記事の収集・解析プロセスにおいて、重要度が高いが現在の `interests.json` には含まれていない新しい概念やキーワードを `learned_keywords` として抽出。これらは一時的なバッファとして `interests.json` に蓄積され、UI上の「AI Insights」タブに提示される。
- **機能 (ライフサイクル)**:
  - **昇格 (Promote)**: ユーザーがキーワードを承認すると、そのカテゴリの正式な `keywords` リストへ移動し、以降のスコアリングやAI探索の対象となる。
  - **却下 (Dismiss)**: ユーザーが不要と判断したキーワードはリストから削除され、ノイズとして処理される。
- **実装の意図**: 「完全自律型」のAI進化は時にユーザーの意図から逸脱するリスクがある。あえてユーザーのフィードバックループ（Human-in-the-loop）を介在させることで、AIの学習精度とパーソナライズの方向性をユーザーがコントロール可能にし、長期的な信頼性を高める戦略を採用している。

### 2.4 インテリジェント多言語サポート
- **自動判定ロジック (`ScraperFacade`)**: 記事タイトルと要約（Snippet）を対象に、正規表現 `/[\u3040-\u309F\u30A0-\u30FF\u4E00-\u9FAF]/` を使用して日本語の有無を判定します。これにより、メタデータが不足しているフィードでも高精度な言語識別が可能です。
- **優先ソートアルゴリズム (`App.tsx`)**: `filteredArticles` において、`language: 'ja'` を持つ記事を最前方に配置します。スコアが同等の場合でも、ユーザーが最も言語的負担の少ない国内情報を最初に見つけられるように設計されています。
- **JA Only フィルタ**: ヘッダーのトグルボタンにより、`isJapaneseOnly` ステートを切り替え、非日本語記事を動的に除外します。

## 3. UI/UX 仕様 & ポリシー
### 3.1 デザイン原則
- **Glassmorphism**: 背景の透過、ブラー（10px〜16px）、微細なボーダー（1px solid white/10%）を組み合わせたレイヤード構造。
- **Non-blocking UX**: AI探索などの長時間処理中もUIのフリーズを回避し、進行状況のみを伝える専用のローディング画面（操作不可・ボタンなし）を提供。
- **Interactive Feedback**: ホバー時の浮き上がり（y-axis offset）、スケールアップ、色の変化によるフィードバック。

### 3.2 画面構成
1. **Intelligence Feed (メイン画面)**:
   - カテゴリごとに整理された記事カードを表示。
   - 表示サイズ切り替え（Small/Medium/Large）。
   - 画像表示のオン/オフ。
   - エージェントのリアルタイム稼働モニター。
2. **Nexus Command (設定画面)**:
   - カテゴリの編集、追加、削除、並び替え。
   - システム設定（APIキー管理）。
   - ナレッジグラフによる視覚化。
   - スキルレジストリ（機能の有効化/無効化）。
   - AI Insights（自律学習されたトレンドキーワードの承認/管理）。

### 3.3 ビルド規約
- **リリースビルドの定義**: ユーザーまたは開発者からの「リリースビルド」指示は、単なるコンパイル（`npm run build`）のみならず、インストーラーのパッケージング（`npm run dist`）までを包含する一連の工程を指します。これにより、即座に配布可能なバイナリが生成されることが保証されます。

## 4. コンポーネント挙動詳細

### 4.1 Unified Editor (統合管理)
- **カテゴリ管理**:
  - **新規カテゴリ追加 (`handleAddCategory`)**: AIにカテゴリの詳細を問い合わせ、ブランド、キーワード、絵文字、理由を元に新規カテゴリを生成。
  - **カテゴリ名の変更 (`handleRenameCategory`)**: `interests` 内のカテゴリ名キーを更新すると同時に、`feed_urls`（フィード設定）側のキーも完全に同期させる。
  - **カテゴリの削除 (`handleDeleteCategory`)**: `interests` と `feed_urls` の両方から関連データを削除。
- **スキル管理 (`Skill Registry`)**:
  - エージェントの機能を個別に有効/無効化。
  - **新規スキルの追加 (`handleAddSkill`)**: スキル名、説明、担当エージェント、スキルの種類（tool/action/logic）を動的に設定し、オーケストレーターの挙動を拡張可能。
- **Deep AI Restructure v2 (堅牢なプロファイル再編)**:
  - `gemini-3.1-pro` を使用し、既存の全設定を分析して最適な10カテゴリに再編。
  - **既存フィードの再割り当て**: 既存のRSSソースを新カテゴリに最適にマッピング。この際、**カテゴリ名整合性強制ロジック (normalizeCategoryName)** を用いることで、AIが生成した名称の揺れによる紐付け失敗を回避。
  - **新規ソースの自動注入**: AIが各カテゴリに高品質なRSSソースを自動発見して追加。
  - **データ完全保持リカバリー**: AIが返し忘れた既存のブランドやキーワードを、再編後に自動的に検知・復元する。
  - **並列検証ロジック**: 従来はカテゴリーごとに順次（シーケンシャル）行っていたフィードの有効性検証を、全カテゴリーで一斉に実行（`Promise.all`）するように刷新。これにより、タイムアウトのリスクを大幅に低減し、再構築全体の所要時間を短縮して UX を向上。
  - **Google News フォールバック戦略**: AIが提案したニッチなURLが検証ですべて全滅した場合、または適切なソースが見つからない場合、そのカテゴリーに最適化されたクエリを用いた **Google News RSS (RSS Search)** を自動的に注入。これにより、再構築後に「空のダッシュボード」が表示されるという最悪の体験を物理的に回避する。
  - **データ正規化 (Data Normalization)**: Geminiの出力は稀にスキーマから微細に外れる（文字列の配列が期待される場所にオブジェクトが来る等）ことがある。v2では `InterestCategory` スキーマへの厳格な変換・クリーンアップ処理をバリデーション直前に挟むことで、Zodによるバリデーション落ち（エラー停止）を徹底的に防止している。

### 4.2 Factory Reset (プロファイルの初期化)
- **Factory Reset (プロファイルの初期化)**:
  - 「System Settings」タブ「Restore Default Profile」ボタンより実行。
  - アプリ同梱の初期設定ファイルを復元し、カスタマイズをすべてリセット（APIキーは保持）。

### 4.3 AI Discovery (探索機能の強化)
- **並列検証**: 発見したフィードの有効性確認を `Promise.all` による並列処理に移行し、探索時間を大幅に短縮。
- **UIフィードバック**: `CustomDialog` に `loading` タイプを導入。AI探索中、ユーザーに進行状況を視覚的に示しつつ、誤操作を防ぐ非ブロッキング・モードで動作。

### 4.4 初回起動時の安全なセットアップ (Setup Guard)
- **初期化フラグ管理**: ブラウザの `localStorage` において `nexus_initialized` キーを使用。このフラグが存在しない場合を「初回起動」と定義。
- **既存データ検知**: 初回起動かつ `interests.json` にカテゴリ定義が存在する場合（ポータブル版の移行や再インストール時等）、即座に動作を開始せず、ユーザーに確認ダイアログを表示。
- **上書きの選択**:
  - **はい（デフォルト復元）**: 既存のカスタマイズを破棄し、最新のプリセットプロファイルを適用。
  - **いいえ（継続利用）**: 既存の `interests.json` や `feed_config.json` を保持したままアプリケーションを開始。
- **意図**: ユーザーが心血を注いで構築したナレッジベースを、アプリケーションのアップデートや環境変更によって不用意に消失させるリスクをゼロにするための保護レイヤー。

### 4.5 APIキー警告バナー
- **表示条件**: `apiKey` が空文字列の場合、エディタ上部に表示。
- **挙動**: 「Configure Now」クリックで「System Settings」タブへ即座にスイッチ。

## 5. システムアーキテクチャ詳細

### 5.1 Electron と Fastify の統合
- **密結合な共有構造**: Electron メインプロセスが Fastify サーバーをインスタンス化して管理。両者は Node.js の同一プロセス空間で動作し、`SettingsManager` という単一のシングルトン・インスタンスを共有。
- **Shared SettingsManager**: フロントエンドからの設定変更要求は、Fastify API または Electron IPC のいずれかを経由し、最終的にこの共有マネージャーが `settings.json` をアトミックに書き換える。これにより、メインプロセスのバックグラウンドジョブ（EvolutionJob 等）と Fastify の API 応答が常に最新かつ同一の設定を参照できる「単一の真実（Single Source of Truth）」を保証している。

### 5.3 OS統合と利便性 (v5.4.0)
- **自動起動機能 (Auto-Launch Integration)**:
    - **仕組み**: `UiSettings` の `autoLaunch` フィールドが `true` の場合、Electron の `app.setLoginItemSettings` API を通じて Windows のスタートアップレジストリに登録される。
    - **制御**: 設定画面（System Settings）のトグルスイッチにより、ユーザーが動的にオン/オフを切り替え可能。
    - **堅牢性**: 開発環境（非パッケージ状態）ではレジストリ操作をスキップするガードを実装し、開発中の副作用を防止。
- **タスクバー・ブランディング**:
    - **アイコン設定**: `BrowserWindow` インスタンス化時に `icon` プロパティへ `public/app-icon-192.png` を `nativeImage` 経由で指定。これにより、Windows タスクバー上での正しいアプリアイコン表示を保証。
    - **インストーラー同期**: `electron-builder` の設定と同期させ、インストール後のショートカットから実行中のウィンドウまで一貫したブランディングを提供。

## 6. エラーハンドリング・ポリシー


1.  **サイレントな失敗の禁止**: 常にユーザーへ通知（Alert）するか、コンソールに詳細なログを出力する。
2.  **APIキー未設定**: AI機能を使用しようとした際、単なるエラーではなく「設定への誘導」を行う。
3.  **保存失敗**: ネットワークエラーやバリデーションエラー発生時は「保存中」状態を解除し、元のデータを復元可能な状態（Draft維持）にする。
4.  **競合防止**: 保存ボタンは変更（Dirty）がある時のみ有効化し、保存中は二重送信を防止する。

## 7. 検証および品質保証

再実装およびメンテナンス時、以下の項目が正常に動作することを必ず検証してください。

### 7.1 フィード取得の正常性 (Critical)
- **全記事更新の検証**: リフレッシュボタン押下後、すべての有効なカテゴリにおいて記事が1件以上ロードされること。
- **並列処理の安定性**: 大量（20件以上）のフィードが登録されている状態でも、フリーズせずにすべての取得が並列で完了すること。

### 7.2 AI機能の正確性
- **網羅性のフォールバック**: ニッチなトピックにおいて提案ソースがない場合、Google News RSS が代替として注入されること。
- **カテゴリ再構築の整合性**: Deep AI Restructure v2 実行後、既存の全購読URLが漏れなく新しい10カテゴリのいずれかに再配置されていること。
